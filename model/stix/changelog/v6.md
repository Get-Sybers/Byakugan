# Extended STIX schema design — byakugan Object Model layer (SCO + SDO + SRO)

Framing per the dogesec guide (fetched): SCOs are the raw evidence ("digital fingerprints", facts without interpretation), SDOs the interpretation ("the what and who"), SROs the connective tissue, with Sighting the specialized SRO for actual observations. Byakugan's model maps onto that split exactly: CAR rows project to SCOs (facts), observations/detections/reconstructions to SDOs (interpretation), and the relationship timeline + behaviour hits to SROs. Normative grounding throughout is the vendored spec `/opt/git/byakugan/docs/standards/stix-v2.1-errata01-csd01-complete.md` (line refs below are into that file).

**The one structural fact the design turns on:** today's wire carries `x_car_*` top-level custom properties and three `x-car-*` custom types (`model/stix/conventions.yml:209,227,116-117`). Custom properties are forbidden in the target model — but §7.3's `toplevel-property-extension` (spec:10293-10310) legalizes the *existing emitted shape* without moving a single property: the objects gain one additive `extensions` entry naming the extension-definition, and every `x_car_*` name becomes a declared extension property. Since no minted id includes those properties (ids come from contributing-property sets and case keys only — `conventions.yml:66-68,106`), the legalization is id-stable *[superseded for the global content-file — see Ratification F2: `extensions` is one of `file`'s ID-contributing properties, so content-files carry no extension entry]*. That is how "custom properties forbidden" and "wire format untouchable" coexist.

### New objects — adversarial justification (invent nothing a standard object + extension can hold)

- **`x-car-thread` → new-SCO: justified.** §6 defines 18 SCO types; none is a thread. Grounding threads to `process` would corrupt process identity (a thread is not a process; its identity key is `[source_host, guid]`, conventions.yml:116). A property extension cannot create an *identity* for a thing that has no host type. Passes §7.3.2's "SHOULD only be used when there is no existing STIX Object" (spec:10440).
- **`x-car-record` → new-SCO: justified.** The fallback observable when a row projects no entity (conventions.yml:117). The only candidate standard type, `artifact`, means raw payload bytes (payload_bin/url) — using it would fabricate content semantics for a record identity anchor. Keep.
- **`x-car-inferred-node` → new-SDO (not new-SCO): the category correction this design makes.** It is "an opinion-style custom object" (conventions.yml:227) carrying `confidence: 20` and assertion flags (:232). Two independent reasons it must be SDO-category: (1) semantics — SCOs "document the facts… without interpretation" (spec:546); a reconstruction is interpretation; (2) mechanics — `confidence` is **N/A on SCOs** (common-property table; conventions.yml:232 already puts confidence on it, which as an SCO would be illegal). As an extension-defined new-SDO it legally carries confidence and remains a valid SRO end (§5.1 source_ref/target_ref MUST point at an SDO or SCO — spec:5747-5754 — SDO qualifies). §7.3 requires all SDO common properties on it (spec:10304) — created/modified come from the as-of rule (conventions.yml `output.as_of`).
- **Rejected new objects:** no `case` SDO (case is an id-scoping construct, `case_ns`, plus a `case_id` extension property; a STIX `grouping`/`report` projection is a future exchange decision, not Object Model); no `incident` (spec:2792 — a stub, and nothing in the contract needs it); no minted `attack-pattern` (below); no "detection" SDO (`indicator` with `pattern_type: car` already is one, conventions.yml:257-260).

## D2 — Extension architecture: TWO extension-definitions

§7.3 gives the rule directly: combine extension types "when appropriate… related" (its hybrid example is precisely a telemetry producer emitting a new SDO + new SCO + property extension, spec:10325-10340), but "SHOULD consider creating separate extension definitions" for independent features (spec:10341-10343). Byakugan has two independent features with different consumers and lifecycles:

**A. `dxdfir` (existing — untouched wire).** `EXTENSION_ID = extension-definition--uuid5(DX_NAMESPACE, 'extension-definition|dxdfir')` (`exchange/objects.py:59-77`), `extension_type: property-extension` only, scope = the detection exchange (indicator/sighting/relationship properties: detection_id, severity, case_id, car_guid, matched, relationship_class — `exchange/extension/dxdfir-extension.schema.json`). Its `$id` (raw.githubusercontent URL), the EXTENSION_ID, and DX_NAMESPACE are wire format — frozen. Evolution is additive within its own schema and semver only.

**B. `dxdfir-evidence` (new).** `extension_types: ["toplevel-property-extension", "new-sco", "new-sdo"]` — one hybrid, because the three parts are one feature (the CAR evidence projection):
- `toplevel-property-extension` + `extension_properties` = the **closed, generated** `x_car_*` list harvested from the **emitted surface** (`byakugan/stix.py` + `conventions.yml` + `objects.yml` — per Ratification F1; conventions.yml alone is not a complete registry). The 54 names: `x_car_action, x_car_analytic, x_car_asserted, x_car_attachment_ref, x_car_base_address, x_car_car_action, x_car_car_object, x_car_class, x_car_clause, x_car_confidence, x_car_conflicts, x_car_content, x_car_content_ref, x_car_corroborated_by, x_car_corroborating_refs, x_car_entity_id, x_car_event_id, x_car_fields, x_car_first_seen, x_car_hosts, x_car_identity_key, x_car_identity_value, x_car_inferred, x_car_inferred_end, x_car_last_seen, x_car_link_confidence, x_car_link_refs, x_car_logins, x_car_method, x_car_names, x_car_native, x_car_node_id, x_car_object, x_car_parent, x_car_path, x_car_paths, x_car_ppid, x_car_process_entity_id, x_car_properties, x_car_reason, x_car_ref_count, x_car_response_body_bytes, x_car_response_status_code, x_car_roles, x_car_signature_valid, x_car_signer, x_car_signers, x_car_source_artefact, x_car_source_host, x_car_techniques, x_car_timestamp, x_car_title, x_car_url_ref, x_car_would_be` (the five engine-only names `x_car_entity_id, x_car_hosts, x_car_title, x_car_car_object, x_car_car_action` gain contract homes at v6). All names satisfy §7.3.2 (lowercase+underscore, ≥3, ≤250 chars — spec:10395-10400); the `x_car_` prefix satisfies the top-level uniqueness guidance (spec:10312). §7.3.1: `extension_properties` MUST only appear with toplevel-property-extension — satisfied.
- `new-sco`: `x-car-thread`, `x-car-record` (type names legal: a-z + hyphen, spec:10404-10406).
- `new-sdo`: `x-car-inferred-node`.

**§7.3 requirement binding:** `created_by_ref` (required) → `identity--uuid5(CAR_NS,'identity|byakugan')`; `id` → `extension-definition--uuid5(DX_NAMESPACE, 'extension-definition|dxdfir-evidence')` (same recipe as objects.py:77 — deterministic SMO id under a producer namespace is §2.9-legal, see D3); `version` (required) → **generated from the Schema Envelope's `schema_version`** — one version, never typed twice (schema-layers.md's ONE-formal-version rule); `schema` (required, normative) → the raw URL of `model/schema/extensions/dxdfir-evidence.schema.json` — on **GitHub** (`github.com/Get-Sybers/...` raw path), per the migration rule; only the *existing* extension's already-emitted GitHub `$id` stays, as wire format.

**Composition with the vendored OASIS schemas (2020-12, no forking):** every object schema is `allOf: [ {$ref: vendor/oasis/<type>.json}, <byakugan overlay> ]` with `unevaluatedProperties: false` at the composed root (never `additionalProperties: false` — schema-layers.md layout rules). The overlay declares (a) the `extensions` dictionary entries for the two extension ids (with `extension_type` const per entry, per the common-properties `extensions` rule, spec:1356), and (b) the `x_car_*` top-level properties — so `unevaluatedProperties: false` closes the shape while the vendored file remains byte-verbatim. The new `x-car-*` objects get their own full schemas (not OASIS-composed — no vendored file exists) that `$ref` the shared common-property `$defs`, since §7.3 requires all category common properties on extension objects (spec:10304, 10393).

## D3 — Relationship schema (the generated SRO shape) and the id rule

### Generated relationship.schema.json

```
allOf:
  - $ref: vendor/oasis/relationship.json          # verbatim OASIS core
  - properties:
      relationship_type:
        enum: [<generated: 55 hyphenated verbs + "indicates">]   # CLOSED
      # …extensions + x_car_* overlay…
    allOf:
      # one per relationship_type, GENERATED from relationship-types.yml:
      - if:   {properties: {relationship_type: {const: attempted-to-authenticate}}}
        then: {anyOf: [ {properties: {source_ref: {pattern: "^process--"},
                                       target_ref: {pattern: "^user-account--|^observed-data--"}}}, … ]}
    unevaluatedProperties: false
```

- **Pair-wise `anyOf`**, not source×target cross-product — the design doc's own finding that for 11 verb names the legal pairs are not a cross-product; each `then` enumerates the declared (source-pattern, target-pattern) pairs. Legs are id-prefix pattern checks (§2.9: ids carry their type prefix, spec:1023).
- **Closed `relationship_type` enum** so undeclared verbs cannot pass vacuously. **Generated, never hand-typed**, from `model/superset/relationship-types.yml` (243 edges) with element→STIX-type resolution via `objects.yml` `sco`/`sro_end` (event objects legally end on `observed-data` — an SDO, satisfying §5.1's "source_ref/target_ref MUST reference an SDO or SCO, never an SRO", spec:5747-5754). **Hyphenation is a MUST, not a style:** the vocabulary's verbs contain spaces ("attempted to authenticate"); §5.1.2 restricts `relationship_type` to a-z, 0-9, hyphen. conventions.yml:205 already says "verbatim (lower-case, hyphenated)" — the generator is the single place spaces become hyphens; the model files keep the verbatim ATT&CK vocabulary.
- **Same-type rules** (ATT&CK's `revoked-by`) stay code checks in `exchange/attack_index.py` — the schema does not model MITRE's own SRO grammar.
- **Declared vs derived marking:** core `labels` + evidence-extension `x_car_class` (`declared|derived`), `x_car_method`, `x_car_identity_key`, `x_car_corroborated_by`, `x_car_inferred_end`, `x_car_properties` (association facts registry, `byakugan/cascade_relationships.yml`), all as declared top-level extension properties of extension B; the exchange's `relationship_class` stays nested under extension A — two layers, two homes, no collision (one is evidence provenance, the other is exchange semantics).
- **Sighting wiring:** `sighting_of_ref` → the indicator (behaviour: the CAR analytic's indicator, conventions.yml:263-268; exchange: the matched feed indicator); `observed_data_refs` → the matched rows' observed-data, **omitted when the row produced none — the sighting still stands** (conventions.yml:266); `where_sighted_refs` → host identity. Sighting's core surface (first_seen/last_seen/count/confidence — §5.2.1, spec:5807-5860) covers the temporal/count facts; everything CAR-specific rides the extensions (A for exchange fields, B for `x_car_analytic/clause/object/action/event_id/source_host/techniques`).

### The id rule (the §2.9 reconciliation)

§2.9 (spec:1017-1029): SDOs/SROs/SMOs **SHOULD** be UUIDv4, **but** producers may use other schemes with "a namespace that guarantees uniqueness" — with one **MUST NOT**: never UUIDv5 under `00abedb4-aa42-466c-9c01-fed23315a9b7` (STIX_NS) for non-SCOs. UUIDv5 under STIX_NS is reserved to SCOs with spec-listed contributing properties. Byakugan needs deterministic ids everywhere (idempotent re-export is a wire contract, conventions.yml:130-135). The rule set to freeze into `constants.yaml`:

- **R1 — global content SCOs:** `uuid5(STIX_NS, RFC8785(contributing))` — spec-native (§2.9), already correct (`stix.py:172` used for SCOs; `ids.py` STIX_NS).
- **R2 — everything case-scoped** (instance SCOs, observed-data, sighting, relationship, x-car-* objects, host identity, bundle): `uuid5(case_ns)` where `case_ns = uuid5(CAR_NS, "case|<case>")` — legal: CAR_NS is a producer-owned namespace ≠ STIX_NS; the SHOULD-deviation is documented (conventions.yml:130-135) and §2.9's uniqueness condition holds (CAR_NS roots a uuid5 tree). Keep, unchanged — wire format.
- **R3 — global SDO/SRO catalogue content (indicator, `indicates`): the one defect this design must name.** the `global_id` helper (`stix.py:172`) mints them `uuid5(STIX_NS, …)` (used at :195 for attack-pattern, :211 for indicator, :843 for the indicates SRO) — a §2.9 **MUST** violation for non-SCO types, independently flagged by the ADM study for the attack-pattern half. Target rule: `attack-pattern` — never minted (airway, R-none); `indicator`/`indicates` — `uuid5(catalogue_ns)` with `catalogue_ns = uuid5(CAR_NS, "catalogue")`. This changes emitted ids, so it does **not** ship silently: it rides the next `model/stix/conventions.yml` contract version (v5→v6, the "changing what is emitted is a separate, explicit decision" rule), and until then the count-and-carry validator tallies each nonconforming id as a finding `{object_id, rule: id-namespace, …}` — visible, not blocking.
- **R4 — SMOs (extension-definitions):** `uuid5(DX_NAMESPACE, "extension-definition|<name>")` — the objects.py:77 pattern, §2.9-legal.
- **R5 — the spindle guid is never an object id.** `uuid5(SPINDLE_NS, …)` (ids.py) rides only in `x_car_event_id` / `native.spindle_key`; SPINDLE_NS sits one level under CAR_NS precisely so row guids can never collide with object ids (ids.py:52-55). One recipe, one seam (`mint()`), no second identity.

Both uuid5 root trees (CAR_NS/SPINDLE_NS and DX_NAMESPACE/EXTENSION_ID) are `constants.yaml` wire constants per the design doc — this schema formalises them, never edits them.

## D5 — Violations to block

1. **OASIS forking:** the tempting shortcut is patching `x_car_*` or the closed enum into `vendor/oasis/relationship.json`. Blocked: vendored files stay byte-verbatim; all byakugan shape lives in the `allOf` overlay, closed by `unevaluatedProperties: false` (never `additionalProperties: false`, which breaks the composition).
2. **Second identities:** (a) never mint `attack-pattern` — the airway owns technique ids (attack_index.py; the ADM study's "DX_DFIR already does it right"); (b) never promote the spindle guid to an object id (R5); (c) no third uuid5 root tree — new namespaces (case_ns, catalogue_ns) only as uuid5 children of the two frozen roots; (d) R3's STIX_NS misuse in `stix.py:172` (helper; call sites :195/:211/:843) is repaired only via a contract-version bump, never silently.
3. **Envelope-version duplication:** `extension-definition.version`, the schema files' `$id` version segment, and the prose "Version 1.1.0" in the existing seed's description are all render targets of the ONE `schema_version` — generated, or the seed's prose demoted to non-normative. Two hand-maintained version markers is the four-ad-hoc-markers bug reborn.
4. **Layer leakage into wire objects:** Artefact Class facets (platform/domain/family/dfir_fields typing) and Parser Profile fields never become extension properties. The only artefact trace on wire is `x_car_source_artefact` + the native provenance bag. The concrete temptation to refuse: a `platform` property on observed-data (class-layer, derivable) and parser field names in ext B (Parser Profile's normalisation seam would collapse).
5. **Custom-property regression gate:** count-and-carry gains two generated rules — any top-level `x_` property not in ext B's `extension_properties` list, and any `x-` typed object not declared new-sco/new-sdo, tallies a finding. That converts today's tolerated custom surface into a monitored, closed one.
6. **Hand-typed vocabulary rot:** the 55-verb wire enum, the tactic→phase table (stix.py's is already stale per the ADM study — TA0005→stealth, TA0112 added), and ext B's property list are all generated from pins (relationship-types.yml, attack-index.json, conventions.yml) — the schema-layers rule, applied to its own extension.
7. **Ref discipline:** `source_ref`/`target_ref`/`sighting_of_ref` never point at an SRO (spec §5.1 MUST); event objects keep their `sro_end: observed-data` discipline (objects.yml:17,322); inferred ends resolve to `x-car-inferred-node`, never to a fabricated SCO of the would-be type (conventions.yml:229-231).
8. **Hosting of the new normative schema:** extension B's `schema` URL and `$id` are GitHub raw paths; only the already-emitted GitHub `$id` of extension A persists, as wire format.

**Bottom line:** one new extension-definition (`dxdfir-evidence`, hybrid `toplevel-property-extension` + `new-sco` ×2 + `new-sdo` ×1) beside the untouched `dxdfir` seed covers every SCO/SDO/SRO need; the 13 CAR objects ground to seven standard SCOs plus two extension SCOs, with predefined STIX extensions absorbing service/socket/http before dxdfir is even consulted; detections ground to indicator+sighting with evidence-edge metadata split core-confidence/labels vs extension; the 243-edge vocabulary ships as a generated closed enum with pair-wise anyOf leg constraints over an unforked OASIS core; and the id rule is frozen as R1–R5 under the two existing namespace trees — with the single latent spec violation (STIX_NS uuid5 on indicator/indicates/attack-pattern, stix.py:172) named, gated by count-and-carry, and scheduled for the next explicit contract version rather than patched into the wire silently.

# Addendum — SMO markings, Bundle packaging, embedded-vs-SRO (completing steps 5-6 of the standard)

Byakugan's pipeline already IS the standard's walkthrough in order: parsed records → SCOs (step 1), observed-data/indicator meaning (step 2), the 243-edge timeline (step 3), inferred-node/identity context + sightings (step 4), TLP marking at export (step 5), one deterministic bundle (step 6). The three sections below pin the two steps the main report under-covered.

## 1. SMO / marking policy — deployment-level, exchange-time, spec-singleton TLP

**What exists (grep evidence):** the car→STIX projection emits NO markings at all — zero hits for marking/TLP/object_marking_refs in `byakugan/stix.py` and `model/stix/*.yml`. TLP lives entirely in the exchange layer, as a **deployment-level constant per export run**: `exchange/config.py:13,76` (`tlp: amber` default; `white|green|amber|red|none`), env `BYAKUGAN_STIX_TLP` (config.py:43), CLI `--tlp` (cli.py:205-206). It is not class-derived and not per-object — evidence sensitivity is a property of deployment/case handling, not of the artefact, which is the correct normalization (a prefetch row is not intrinsically AMBER).

**The rule, as the schema declares it:**
- `mark()` (`exchange/objects.py:439-445`) attaches `object_marking_refs` to SDOs, SROs and observed-data; **SCOs are never marked** ("mark the Observed Data, not the address" — BP §3.5; `SCO_TYPES` objects.py:105-110), nor are marking-definition / extension-definition / bundle (`_UNMARKED_TYPES`, objects.py:111).
- The four TLP marking-definitions are **spec-defined singletons with fixed ids** (§7.2.1.4, spec:10086: "The following standard marking definitions MUST be used… Other instances of tlp-marking MUST NOT be used or created"). Byakugan **references, never emits** them (objects.py:93-94; `tlp_marking()` docstring: "Never put in a bundle (BP §3.5)") — so the SMO row of the coverage matrix reads: marking-definition = referenced singleton, in the model but never in the byakugan-produced object set, exactly like the airway's attack-patterns.
- Schema overlay: `object_marking_refs` is already an optional common property in the vendored OASIS core, so under `allOf` + `unevaluatedProperties: false` it validates with **no overlay declaration needed**; the overlay adds only a generated enum restricting its items to the four fixed TLP ids, so a fabricated marking id fails validation.

**Defect found:** `objects.py:99` pins TLP:AMBER as `marking-definition--f88d31f6-dadc-4b46-af9e-88246e2fbd0c`, but the spec's fixed TLP:AMBER id is `marking-definition--f88d31f6-486f-44da-b317-01333bde0b82` (spec:10122-10125). White, green and red match the spec exactly (objects.py:97-101 vs spec:10094/10108/10136); amber — the **default** level (config.py:76) — does not. Every default export therefore marks objects with an id that is not the TLP:AMBER singleton and, under §7.2.1.4's MUST NOT, is an illegal TLP instance; since markings are referenced-never-emitted, the reference also dangles for any consumer resolving against the spec singletons. The correct id was never legally mintable, so this is defect repair, not wire evolution — but it changes emitted bytes, so it rides the explicit-decision route (exchange contract bump), with the generated four-id enum preventing regression and count-and-carry tallying the bad id until repaired. [Orchestrator verification: confirmed first-hand — byakugan/exchange/objects.py:99 vs spec line 10122; white/green/red match their singletons.]

## 2. Bundle — contents, id rule, validation

**Two bundles, two deterministic id recipes:**
- Car projection: `{"type": "bundle", "id": case_id(ns, "bundle", case), "objects": [...]}` (`stix.py:898-903`), keyed `[case]` — confirmed at `model/stix/conventions.yml:121` — with fixed ordering (identity, SCOs by type/id, observed-data by time, inferred nodes, relationships by time, then behaviour layer; stix.py:149-153) so re-export is byte-identical.
- Exchange: `bundle_id()` = uuid5 over the sorted member ids (`exchange/export.py:312-314` — "the same content is the same bundle"), content-keyed because merged multi-producer bundles have no single case.

**Contents (all four categories):** SDOs — producer + host `identity`, `observed-data`, `indicator`, `x-car-inferred-node`; SCOs — the seven standard groundings + supporting atoms + `x-car-thread`/`x-car-record`; SROs — the 243-vocabulary relationships, `indicates`, sightings; SMOs — **both extension-definition objects ride in-bundle** (§7.3 says consumers must otherwise resolve externally; byakugan includes them — built at objects.py:264, and `validate_bundle` enforces "extension definitions present" with their §7.3.1 requireds, export.py:24-31,65-66). **Not in-bundle, by design:** the four TLP marking-definitions (spec singletons, BP §3.5) and MITRE's attack-patterns (the airway — "only identifier references need to be shared", attack_index.py docstring; `validate_bundle` treats ATT&CK references as non-local by design, BP §3.3, export.py:25-27). The car projection still minting attack-patterns in-bundle is the R3 migration item from the main report.

**Validation vs ADM's dead code:** ADM's `stixBundleSchema` is a 15-schema discriminated union that omits `relationship` and `marking-definition` — "a real ATT&CK bundle (21,262 relationships) can never pass it, and ADM's own loader quietly routes around it" (`docs/research/attack-data-model-alignment.md:293-297`); the keeper is the minimal bundle-level contract `{id, type, objects: [≥1]}` with **no bundle-level spec_version** (study:282-286). Byakugan's rule: the bundle schema validates only that minimal envelope; each member is validated by **type-field dispatch** to its per-type composed schema (OASIS core + overlay); unknown types and failed objects become count-and-carry findings `{object_id, rule, path, message}` — never dropped ("nothing is dropped for being unfamiliar", export.py:20-22) — and strict mode fails `--check` on a nonzero tally. No discriminated union exists to rot.

## 3. Embedded `_ref`/`_refs` vs SRO — the explicit table

Rule of thumb applied verbatim: **embedded = spec-defined structural link; SRO = analyst/derivation insight.** Byakugan adds a sharper third clause: extension-carried ids are provenance pointers, never a graph channel — "every SRO comes from the relationship timeline", and nothing re-derives an SRO or an embedded `_ref` from `native` (conventions.yml:296-297).
